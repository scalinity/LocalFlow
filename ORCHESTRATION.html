LocalFlow V2 — orchestration overview

LocalFlow is a private, local-first macOS dictation and writing interface built around Parakeet TDT 0.6B V3 via MLX and Qwen3-4B-Instruct-2507 4-bit via MLX. V2 closes the gap with Wispr Flow while preserving local inference and training-ready data collection. This page is the dispatch board for that build: what can run next, in what company, on which model, and against what standard of proof.

Marginal value, never importance

The model-allocation rule

Two models exist in practice: the scarce model (the quota-limited strong one) and the plentiful model (fast and cheap). The scarce model goes where its marginal value is highest — not where the work is most important. This repository records no per-unit model history, so every dashed chip on the strips above is this chart’s recommendation, never a repo fact.

Is there a precedent to copy?

No repo precedent for this kind of unit means the first author sets the pattern for everything after it.

In the record: M09 shipped the first native AppKit shell (d10886c) — there was no prior unit to imitate. M12’s notes editor, by contrast, composes M09’s patterns.

Will later work live inside this decision?

Contracts, schemas and precedence rules are cheap to set once and expensive to revisit after dependents exist.

In the record: M04/M05 policy precedence; M08’s insertion-authority semantics now feeding M09’s replay/paste-again and later M14 attribution; M13’s denominators reused by M14.

Can a wrong version be undone cheaply?

A step that cannot be reversed — or that replaces the only working copy of something — justifies the scarce model up front.

In the record: M16’s staged swap retires the installed pre-M02 app, the only deployed copy; M15 changes default models only behind promotion gates.

Any yes above → scarce authorsThe scarce model writes that contract, harness or decision; the plentiful model builds everything around it.
All no → plentiful authorsFixture bulk, view implementation, run execution, checklist work — even when the unit as a whole is critical (M16’s acceptance matrix).
Near the line → scarce reviewsWhere a unit sits between the two, the plentiful model authors and the scarce model reviews the diff — that is how the quota stretches.

The evidence that review is worth spending scarce-model attention on: twelve closed milestones, twenty-five review criticals, every one of them real and every one fixed in-session — see the record below.

One milestone, one fresh session

The per-unit session loop

Every closed milestone followed this loop; the handoffs record it explicitly, including the one deliberate adaptation (the /address per-fix commit cadence became one close-out commit, no push, per each kickoff’s constraints).

Fresh session, pasted kickoff. The P06 template names one milestone id and nothing else; it needs no prior conversation.
Startup order. STATUS.json, then the milestone section and its listed spec/evaluation sections, then the contract index and prerequisite handoffs — not the whole repository.
Baseline first. Branch, base commit, local modifications confirmed; owning tests run before any edit; pre-existing failures recorded separately.
Implement the approved scope only. A short execution checklist with requirement and suite ids; nothing speculative.
Run required tests and benchmarks. Commands, environment, dates, exit codes and result paths recorded; a mock never substitutes for a native or model benchmark.
/review-2. Two parallel read-only reviewers — a bug-hunting debugger and an architecture/quality/security/data-integrity auditor — deliver a verdict before anything is touched.
/address. Criticals and warnings fixed in-session with regression tests; deferred suggestions carry written reasons in results.json.
Re-run on post-review code. Every suite, the model-backed checks and the benchmark, on the fixed code — never on the pre-review state.
Close-out artifacts. Handoff Mxx.md, acceptance results.json, contract index updates, STATUS.json — all written from actual work, dirty trees recorded honestly.
One commit, no push. The milestone lands as a single close-out commit; pending human checks stay pending with exact steps.
Next kickoff printed last. The handoff ends with the next eligible milestone’s copyable prompt — the loop’s actual output.
…and the next session pastes that kickoff into a fresh context. Stop conditions from P04 apply throughout: completion of assigned scope is the normal stop point; a failing test is implementation work, not a reason to lower the bar; pending human verification is not permission to abandon remaining automatable work.

The completion-report contract (P03 — the close-out checklist every handoff must satisfy): scope and requirement ids; final branch/base/current commit; actual files changed; decisions and contracts; commands and tests with results; benchmark environment and measurements; acceptance item status; human checks pending/completed; known limitations; unresolved issues; spec deviations; rollback instructions; private-data handling; notes plus the next kickoff. Reports distinguish implementation, automated verification, native verification and user approval — 600–1,000 words plus linked structured output, never pasted logs. LOCALFLOW_V2_MILESTONES.md P03

The bar a new session’s output must meet

Grading a new model against the standard already set

  • Counts come from the registry, never hand-counted. 33 requirements / 22 suites / 0 without a suite, machine-derived from the S05/E08 tables; regenerate with scripts/v2/build_registry.py and cross-check with tests/v2/test_registry.py. A hand-quoted count is a defect.
  • An unrun check is never reported as passed. The START_HERE rule, held by every closed milestone (M01–M14): each unavailable human check appears in results.json as pending with exact steps — sixteen are open right now, and M16 cannot claim verified_complete while required checks remain.
  • Unknowns are null with a reason. The deleted producer sources and the instance.lock mystery are recorded unresolved in the baseline manifest rather than guessed — “recorded, not forced,” as M01 put it.
  • Exact denominators, always. The M05 hint matrix reports its 40 labeled bases × 4 conditions; the M04 command corpus reports 16/16 exact and 0/8 false commands; M15’s plan pins 140 clips + 20 negatives before any score is quoted. A percentage without its denominator does not ship.
  • The review bar is verdict-first and fixes-forward. /review-2 records its verdict before /address touches anything; criticals and warnings are fixed in-session with regression tests; deferrals carry written reasons; all fourteen records to date end “no findings rejected as incorrect.” Accepting a verdict without fixing, or rejecting findings as incorrect without evidence, fails the bar.
  • Report kinds stay separated. Implementation, automated verification, native verification and user approval are distinct claims (P03) — “model-backed native Mac” and “human-approved” are never blended into one word like “tested”.
